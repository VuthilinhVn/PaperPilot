# Paper 阅读平台后端设计说明

## 1. 项目目标

为现有 Vue 3 + Vite 前端提供论文浏览服务。项目以 arXiv paper 数据为核心，支持按分类浏览论文、查看摘要和 PDF、用户注册登录、论文收藏和浏览历史。

本项目不是新闻系统。新闻分类、新闻内容、新闻图片及 `newsId` 等概念不再用于业务 API。已有账户功能和账户数据模型可继续使用；收藏与历史记录的关联对象改为 paper。

## 2. 现有项目和数据事实

- 前端 API 基础地址当前配置为 `http://127.0.0.1:8000`，配置位置：`src/config/api.js`。
- Paper API 响应使用 `{ "code": 200, "msg": "success", "data": ... }`，与当前 FastAPI router 示例一致。
- `import_to_db.py` 将 CSV 数据导入 MySQL 数据库 `papers_app` 的 `papers` 表。
- 导入字段：`paper_id`、`title`、`abstract`、`first_author`、`primary_category`、`submitted_date`、`arxiv_url`、`pdf_url`。
- 分类通过 `paper_primary_category` 表关联；导入脚本使用分类显示名称写入该表，例如 `Computer Vision`。
- CSV importer 当前允许 15 个 arXiv 分类。前端无可用分类接口数据时默认展示 7 个：CV、ML、NLP、AI、Robotics、IR、Neural and Evolutionary Computing。后端接通后分类列表应以数据库/API 实际返回为准。
- Paper detail 使用 camelCase 字段 `id`、`title`、`abstract`、`author`、`publishTime`、`categoryId`、`relatedNews`；需额外返回 `pdfUrl`（映射数据库 `pdf_url`），供详情页 iframe 加载。
- 详情页直接将 `pdfUrl` 放入浏览器 `iframe`，不把 PDF 文件传到前端服务器内存，也不将 PDF 内容存进数据库。

Paper detail 示例中的 `id: 1` 按 `papers` 表数据库主键处理；收藏与历史请求的 `paperId` 也传这个主键。CSV/arXiv 外部标识 `paper_id` 是另一字段。实现前仍须核对实际建表 SQL，特别是主键、分类外键及用户关联表。

## 3. 技术栈建议

- Python 3.11+
- FastAPI、Uvicorn
- SQLAlchemy 2.x Async ORM、`aiomysql`
- Pydantic v2
- MySQL 数据库 `papers_app`
- 密码哈希：`pwdlib[argon2]` 或项目统一采用的安全哈希实现
- 认证：随机不可预测的 token + 服务端过期时间；如采用 JWT，应验证签名、过期时间和算法
- Redis 为可选缓存。先保证数据库读取正确，再为列表、详情和分类增加缓存。

连接字符串、token secret、Redis 凭据等通过环境变量或未纳入版本控制的配置提供，不得写入代码或提交到仓库。

## 5. 功能范围

### 5.1 论文

- 查询实际存在的论文分类。
- 按分类和分页查询论文列表。
- 按论文标识查询论文详情，返回摘要、作者、提交日期、分类和 PDF/arXiv URL。
- 返回浏览器可访问的 PDF 直链。若以后需要鉴权、私有存储或下载统计，再增设 PDF 代理接口。

### 5.2 用户账户（保留既有功能）

- 注册、登录、获取个人信息、更新个人资料、修改密码。
- 密码只保存安全哈希；接口禁止返回哈希或 token secret。
- 已登录请求继续使用前端当前格式：`Authorization: <token>`（不带 `Bearer ` 前缀）。

### 5.3 收藏和浏览历史

- 收藏和历史关联到论文标识，不关联新闻。
- 用户只能查看、删除自己的收藏/历史。
- 相同用户和论文的收藏保持唯一。
- 重复浏览同一论文时更新其浏览时间并将其排到列表最前。

## 6. 数据模型建议

最终列名以已有 migration/数据库结构为准。以下是约束和关系建议，而非要求重建现有数据库。

### `papers`

- 数据库主键 `id` 用于前端详情路由、收藏和历史关联；CSV/arXiv 外部标识保留在 `paper_id`。
- 字段至少覆盖 importer 写入的论文标题、摘要、PDF URL、arXiv URL、首位作者、分类外键和提交日期。
- 若 `paper_id` 在 CSV 中唯一，应对该列建唯一索引；分类外键建索引。
- API 的 `id` 表示数据库主键；可额外返回 `paperId` 表示 CSV/arXiv 外部 ID。

### `paper_primary_category`

- `id` 为数据库分类 ID，`name` 为 importer 写入的规范显示名称。
- `name` 建唯一约束。
- 可在 API 增加 `code`（如 `cs.CV`）；当前 CSV importer 存入分类显示名称，分类 code 不一定保存在表中，不能在无数据依据时伪造 code。
- 分类列表只返回数据库中实际存在且有论文的分类；如果需要固定 7 类，应由业务配置明确筛选，不应把虚构分类返回给前端。

### 用户、收藏、历史

- 用户表唯一用户名，密码哈希和账户资料分列保存。
- `favorite`、`history` 都使用 `user_id` 和 paper 数据库主键建立关联；关联列即使命名为 `paper_id`，其语义也应与 API `paperId` 一致。
- 收藏唯一约束 `(user_id, paper_id)`；历史可对 `(user_id, paper_id)` 唯一，重复访问时更新访问时间。
- history 记录有自己的记录标识 `historyId`；它与论文 `id` 是不同标识。API 列表应同时返回两者。
- 收藏和历史记录均应有创建/更新时间字段并建立用户、论文索引。

## 7. API 和前端对接约定

API 路由和字段以 [API接口规范文档.md](./API接口规范文档.md) 为准。关键对接要求：

1. Paper 成功响应使用 `{ "code": 200, "msg": "success", "data": ... }`。
2. 论文分类：`GET /api/papers/categories`；列表：`GET /api/papers/list`；详情：`GET /api/papers/detail?id=<paper-database-id>`。
3. 列表支持 `categoryId`、`categoryCode`、`page`、`pageSize`。`categoryId` 为数据库分类 ID；`categoryCode` 可选。若两者都传，优先按合法的 `categoryId` 过滤；不要因 code 未保存而误返回其他分类论文。
4. Paper detail 按现有 schema 返回 `id`、`title`、`abstract`、`author`、`publishTime`、`categoryId`、`relatedNews`，并增加 `pdfUrl`；可选返回 CSV/arXiv 外部 ID `paperId` 和 `arxivUrl`。`id` 是 paper 数据库主键，不得误用 favorite/history 关系记录 ID。
5. favorite add/check/remove 接收 `paperId`；history add 也接收 `paperId`。前端历史删除请求使用 `DELETE /api/history/delete/{history_id}`，其中 path 值是历史记录自身 ID。
6. 收藏列表返回论文对象，并提供 `favoriteTime`；历史列表返回论文对象，并提供 `historyId` 和 `viewTime`。建议将论文对象放在 `paper` 属性中，避免论文 ID 与关系记录 ID 混淆。
7. 所有需要登录的路由应返回标准 401；其他服务错误不可伪装成空列表或成功。

## 8. PDF 展示和部署注意事项

- 数据库 `pdf_url` 在 Paper detail 响应中映射为 `pdfUrl`。详情页把它赋给 `<iframe src>`，浏览器直接向该 URL 发起 GET；后端只负责返回 URL。
- URL 应使用浏览器可访问的绝对 HTTP(S) 地址或同源路径。开发环境内网地址、容器内部地址或本机 `localhost` 通常不能被其他终端浏览器访问。
- PDF 主机必须允许正常访问，并返回 PDF 内容及合适的 `Content-Type: application/pdf`。若目标站点通过 `X-Frame-Options` 或 CSP 禁止被嵌入，浏览器 iframe 会拒绝显示；详情页提供“在新窗口打开”作为回退。
- arXiv 的 `/abs/<id>` 可转换为 `/pdf/<id>`，但优先返回 importer 中的 `pdf_url`（API 字段 `pdfUrl`）。
- 若浏览器因跨域策略、访问控制、URL 过期或源站策略无法加载，须明确返回/显示错误；不要声称前端已经下载 PDF。需要代理时另行设计安全的流式下载端点，验证目标域名并防止 SSRF，不接受客户端任意 URL 作为代理目标。
- 前端开发服务默认需允许 Vite 开发源访问后端。仅对明确的开发/生产前端域名配置 CORS，不要使用带凭据的通配来源。

## 9. 安全、错误和验证

- 对用户名、密码、分页参数、ID、资料字段做长度/类型/范围校验；密码采用安全哈希。
- 使用 ORM 参数绑定，避免拼接 SQL；用户数据按当前 token 所属用户过滤。
- 不记录密码、token 或数据库凭据；对登录、收藏/取消、删除操作做合理审计/限流。
- 统一处理未授权、资源不存在、重复数据、校验失败和数据库异常。HTTP 状态码语义正确；响应体提供稳定 `code` 和可读 `message`。
- 建议先验证：DB 连接/导入数据读取、paper categories/list/detail、PDF URL 可达性、收藏幂等性、history 更新排序、账户授权隔离。
- 由于当前仓库未包含后端代码或完整建表 migration，ORM 映射和外键列名必须在实现时对照实际数据库确认。

## 10. 缓存建议（可选）

- 分类：短期缓存；数据库发生分类/论文数据变更时失效。
- 论文列表：缓存键需包含分类、页码、每页数量和排序规则。
- 论文详情：按稳定 `paper_id` 缓存；论文 URL/元数据更新时失效。
- 用户收藏、历史数据须按 `user_id` 隔离；不要缓存为所有用户共享的数据。
- 初期可以不引入 Redis，先实现正确性和数据库索引，再根据实际负载决定。
